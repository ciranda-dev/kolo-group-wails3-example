# How it works

Kolo Group is an example app. The room is built in `internal/room`: creating a room, adding and removing members, promoting a second admin, sending and reading messages live, storing them for the offline in the admins' segments, catching up after an absence, reading the room's history after joining it, and reopening every room after a restart. The window does not use it yet, and everything marked planned is not built.

## What is built

- **A room is an MLS group** (RFC 9420, kolo-mls). Every member device is a leaf of the tree. The creator is the room's first admin and settler; the admins' braid (kolo-braid) orders each change of the group and a SettledCommit proves that the settlers agreed to it.
- **Create, Add, Remove and Promote.** `Create` makes a room with its history rule (see History). `KeyPackage` makes what a device hands to an admin. `Add` takes key packages, makes one Commit for all of them, waits until it is settled and applied, and returns one welcome for the new devices, who enter with `Join`. `Remove` removes every device of a person. `Promote` makes an online member device a second admin (see below). Each change is one new epoch.
- **Live delivery.** A message is sealed and sent on the room's gossip topic (kolo-gossip) to the members online. Every member is a gossip author because it is a leaf of the tree: the roster is read from the tree of the current epoch and of the previous one for a short window, so there is no second member list. A device publishes at most four fifths of the rate its peers accept and waits for the rest, so it is never rejected for sending too much.
- **Sealing.** The key of an epoch, K_e, is exported from the MLS epoch: `Export("kolo-group/history/v0", group id and epoch, 32)`. A message is padded and sealed with XChaCha20-Poly1305 under K_e, with a random nonce, and its additional data names the room, the epoch, the sending device and the sequence number. The sending device signs the sealed message (Ed25519, context `kolo-group/author/v0`), so a copy of it that sits in a log proves who sent it without the gossip envelope. The id of a message is a hash of the room, device, sequence number and sealed body, so every holder of a copy computes the same id.
- **The validator.** Before a node forwards a message it checks the author's signature, the epoch (the current one, or the previous one for a short window, or an older one the device holds when a member publishes its own message again), the sender's rate, the body (it opens it), the number of parents and the time. A message that no honest member sends is rejected, so its sender and the peers that sent it lose score; one that is only out of date is ignored.
- **Order.** A message carries the id it answers (`ReplyTo`) and the ids its author had shown (`Parents`), the author's own previous message first. `Next` shows a message after every message it names that this device knows. A message whose parent has not arrived waits a short time, then shows. `Display` gives the same order to everyone who holds the same messages. Messages read from a segment go through the same order as live ones.
- **Admission.** `Node.Allow` is the swarm's admission rule: only devices that are leaves of a room of this node connect. A connection of another device that gets through is closed by `ServeConn`. When a device is removed its connections are closed, and it forgets the room: its stored keys and logs are deleted and a restart does not reopen it.
- **One connection.** `ServeConn` puts a tag byte at the start of every stream and gives each part its own view of the connection: gossip on unidirectional streams, kolo-sync on bidirectional ones, and the admins' braid on both.
- **Commits** travel on the room's topic as one message with the SettledCommit, and are also written to the control logs below. A member applies one only with the settlers' signatures. A Commit that does not fit one gossip message is refused when it is made.

### History

- **A key for each epoch, a link between neighbours.** Each epoch has the key K_e of Sealing. When an admin enters epoch e it writes a history link to its control log: the key of epoch e-1 sealed under K_e (XChaCha20-Poly1305, additional data the room and e, 72 bytes). A device that holds K_e opens the link and holds K_(e-1), then the link of e-1, and so on back to the oldest epoch the rule allows, so one key opens a range of epochs. A device that joins in epoch J holds K_J from its Welcome and walks back only as far as it reads. Keys it derives are kept in its store, so a restart does not walk again.
- **The rule** is chosen in `Create` and recorded in a GroupContext extension (type 0xF003, next to the roles), which every settled Commit signs and every Welcome carries: `AllHistory` (the default), `SinceEpoch` with an epoch P, or `NoHistory`. Under `SinceEpoch` no link is written for an epoch up to P, so the key of epoch P-1 is out of reach and a joiner reads from epoch P; under `NoHistory` no link is written. A room without the extension keeps all its history. The rule is never retroactive: a link is valid only if its epoch is allowed and its admin wrote it before any segment of that epoch or a later one in the same control log; any other link is refused and reported with `ErrLink`.
- **`History(ctx, before, n)`** returns up to n messages older than `before`, oldest first, from the epochs before this device joined. The zero id starts from the newest; any other must be the oldest message of the page the last call returned. It loads one epoch at a time, newest first: it derives the key, follows the segments that the admins' control logs name for that epoch, waits until they are complete (from the admins, other members or the pins, for at most `CatchUpWait`), reads them in the causal order of `Display`, and forgets them. A message that cannot be read (a bad signature, a key that does not open, an author the room has no certificate for, an epoch outside the rule, a segment shorter than its admin declared) is an `Event` with `Err` set and `ErrCatchUp`, never left out. When no link opens the next key, `History` returns `ErrHistory`. A message of an epoch before the join never shows in `Next`, even if an admin stored it in a later segment.
- **Joining late.** A device that joins at epoch 40 follows the admins' control logs from their first entry, and reads epochs 1 to 39 with `History`. The room tests do this over 40 epochs.

### Segments

- **Each admin device writes two kinds of kolo-log log** (one writer each, entry keys derived from a secret every member holds, so a pin or any peer serves ciphertext that every member opens):
  - the **control log**: the Commits and SettledCommits the admin saw settle (`settle.Pins` is implemented over it), the opening and closing of each segment with its final size, and the control logs of the other admins it knows;
  - **segments**: every message that passed the validator, as it travelled (device, sequence number, signed sealed body). A segment is written in one epoch (a message of the epoch before that arrives late goes into it with its own epoch) and holds at most `SegmentEntries` entries; it is closed in the control log when its epoch ends or it is full.
- **Pins.** An admin pushes the logs it writes to the pins with kolo-pin `AddMany`, at most once a second for each log, under a capability that only its device key can present. A pin never joins the topic and never writes a log.
- **Members follow and serve.** Every member follows the control logs of the admins and their segments from the epoch it joined on, with kolo-sync, pulls each from the connected peer with the largest verified head, admin or member, derives the entry keys, and offers what it holds to the other members of the room and to nobody else. An admin is not needed once its logs are held.
- **Stored receipts and republishing.** A device that is no admin keeps each message it sends until a segment holds it, shows a `Stored` event when one does, and publishes it again in a new envelope after `RepublishAfter` while none does. A message sent while the admins were away is stored when one returns. A segment never holds a message twice. Receipts survive a restart and are bounded by `MaxReceipts`.
- **Catch-up.** A device that was away reads the control logs it was missing, applies the settled Commits one epoch at a time (each epoch gives it that epoch's key), and reads the segments, from the connected peers, and from the pins only when no other admin has been connected for `PinWait` or nothing has grown for `PinWait` while it is behind. While it asks the pins it pulls every log it is behind on once each `PinWait`, and it lets them go once an admin is back and it is current. An entry it cannot read, verify or open is reported as an `Event` with `ErrCatchUp` and the cause and is never shown or skipped without a report; a segment that its admin closed with more entries than anybody holds is reported after `CatchUpWait`. A SettledCommit that does not apply is reported once and the next admin's is tried.
- **Restart.** Rooms, MLS state, epoch keys, the authors of every device the room had, logs, receipts and the braid are kept in the stores and reopened by `Open`. An admin goes on with the segment it was writing.
- **A second admin.** `Promote` publishes an offer on the room's topic; the device makes its control log and a join request for the admins' braid and publishes them; the admin admits it to the braid, the device completes the join, and a Commit changes the roles. From that epoch the device writes segments and commits as the first admin does; it is not a settler, so the first admin still settles every Commit. Only the role Admin is built.

## What is not built

- **Roles and the rest of the policy** (planned, T-L16): `Promote` to `Settler`, `SetPolicy`, posters, the read link and `JoinLink` return `room: not implemented`; `Create` refuses posters and a read link. The history rule cannot be changed after `Create`.
- **Authors that left before the join** (not built): a joiner holds the certificates of the devices that are, or were since it joined, in the room. A message of a device that left earlier is reported by `History` with `ErrUnknownAuthor`, since no library gives the credentials of past members.
- **Commits by reference** (planned, T-L7): a Commit and its SettledCommit still travel in one gossip message and are written as one control log entry, so one that does not fit `MaxMessageSize` is refused.
- **The encrypted tree served by members** (planned, T-L8): trees stay on the admin that sealed them, and a joiner's tree comes in its invite. A device that applied an epoch from another admin's Commit seals the tree when it adds.
- **Hints of new heads on gossip** (not built; the kolo-sync watch already tells every connected peer when a log grows).
- **Leave, the window, invites and `-headless`** (planned).
- **Wake-up of offline devices** (planned, needs the mobile apps).

## Design that is planned

- **One design for every group size.** The app has no group size, mode or threshold. The 64-device tests below are the largest run.
- **Read-only members and a read link** (planned). A room can list who may post. A room with a read link lets anyone with the link read, with no secrecy.
